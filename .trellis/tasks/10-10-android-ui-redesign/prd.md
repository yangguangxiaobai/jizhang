# Android 全界面 UI 与动效重构规划

## Goal

按现有功能规划整个原生 Android 客户端的 UI 重构，形成可读、可实施、逐页可验收的本地 README。用户明确要求本次只做规划，允许适当调整界面组织，并要求动画十二原则。

## Background

- 客户端为 Kotlin/Compose，代码在 `clients/android/`，最低 API26。
- 当前有六个底部入口，`MyTab.kt` 集中管理大量二级功能，多个页面混合列表和编辑。
- 默认域名 `jz.yansuu1.xyz`，生产已按原任务切至 API-only；本任务不重新部署。
- 源码核对和旧规范冲突见 `research/source-audit.md`。

## 2026-10-10：实际功能盘点与长期维护文档

用户反馈现有改造效果不满意，要求逐项探查当前 App 的全部功能，生成需要持续维护的 README。本轮目标变更为源码功能审计及文档交付，不追加 UI 改动。

- 唯一当前功能目录：`clients/android/README.md`，中文，按实际功能而非设计页面划分。
- 覆盖主入口、全部二级页、表单字段/校验、操作/返回、状态、分页筛选、文件、认证、设置、AI 工具及对应后端接口。
- 区分客户端已接入、后端独有、间接可用、字段漏显/源码问题和设备待验证；设计文档不得作为实现证据。
- 保存稳定功能 ID、源码链接、全 main Kotlin 文件和全部 route 文件的覆盖表、已知问题清单、更新日期及变更日志。
- 将同批更新规则写入项目指引，并在根/client README 添加入口；不承诺后台自动更新或不存在的服务。
- 审计原始依据留在 `research/function-inventory-*.md`；只改文档，不构建、不部署、不修改账务数据，不将文档完成等同于全 UI 验收完成。

验收：全部审计条目被目录收录；链接有效；功能 ID 不重复；所有正常入口和服务接口均有覆盖或明确排除理由；事实与设计/实测清晰区分；维护指引可被后续开发者发现。
