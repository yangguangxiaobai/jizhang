# 数据导出与导入 — 技术设计

> 前置阅读:`prd.md`、`.trellis/spec/backend/quality-guidelines.md`

## 1. 关键约束与由此推出的设计

| 约束 | 推出的设计 |
|---|---|
| 项目不引依赖(图表手写 SVG) | CSV 编解码**自己写**,放 `packages/shared`(纯函数 + 单测) |
| Excel 在 Windows 按本地代码页解析无 BOM 的 UTF-8 | 导出 **UTF-8 + BOM**;这是可实测的,不靠猜 |
| 金额必须是整数分;`19.99*100` 有浮点误差 | 导出用既有的整数算法生成"元"字符串;导入用 `Math.round(value*100)` |
| 日期字符串 `new Date(str)` 按 UTC 解析会偏移一天 | 导入按**本地日**解析,与 `fromDateInputValue` 同一口径 |
| `restoreBackup` 强制停服才能恢复 | **UI 不提供恢复**;只给指引(§5) |
| 备份保留期逻辑已存在 | 复用 `createBackup(dbFile, dir, retainDays)`,不新造 |
| 前端只渲染 | CSV 在服务端生成;前端只下载/上传 |

## 2. 决策一:CSV 库自己写

需要的能力只有两件:**转义一个字段**、**把一行拆成字段**。RFC 4180 的规则很小:字段含逗号/引号/换行时用双引号包裹,内部的双引号写两遍。

引入一个 CSV 依赖的代价:多一个包、多一份安全面(解析库的历史漏洞不少),而收益是省下约 60 行代码。项目的既定取向很明确(两个图表都是手写 SVG),这里照做。

放 `packages/shared/src/csv.ts`:
- `encodeCsvField(value: string): string`
- `encodeCsv(rows: readonly (readonly string[])[]): string`
- `parseCsv(text: string): string[][]`

**解析器必须处理**:引号包裹的字段内的逗号、转义的双引号、字段内的换行、CRLF 与 LF 混用、以及结尾无换行。每一条都有单测——这是最容易被"看起来能用"的简化实现坑到的地方。

## 3. 决策二:去重键用导出携带的 `id`

**结论:用 `id`。**

备选是"日期 + 类型 + 金额 + 备注"这类自然键。它错在**误判合法的重复**:同一天买两次同样的咖啡是真实发生的,自然键会把它当成重复而丢弃一条。而丢数据是这个功能最不可接受的失败。

`id` 是导出时写进 CSV 的主键。导入时:
- 该 `id` 在本库已存在 → **跳过**(计为 `skipped`)
- 不存在 → 插入(保留原 `id`)

保留原 `id` 是刻意的:它让"导出 → 导入 → 再导入"永远幂等,也让用户能在两次导入之间对比同一笔账单。这与 `budget_allocations` / `occurrences` 的引用不发生冲突,因为**导入不涉及那些表**。

**已知局限(写进 spec)**:若用户在两个库里各自录入了账单,再合并导入,同一天的两笔不同账单会各自保留(因为 `id` 不同)——这是正确行为;但同一个 `id` 被两个库各自修改过时,导入会**跳过**而不做合并。本任务不做冲突解决(D4/D7 也排除了多设备同步)。

## 4. 决策三:批量导入全成或全不成

**结论:单事务,全成或全不成。**

理由:
- 本应用是单用户本地 SQLite,导入的失败来源几乎只有**文件本身有问题**(金额非法、缺列、引用了不存在的分类)。这类失败是"整份文件不对",不是"第 37 行碰巧不对",部分提交只会留下一个用户难以理解的半成品账本。
- 部分成功要求 UI 表达"新增 120 条、失败 3 条、它们分别是……",而这 3 条的原因通常相同。

因此:**任何一行校验失败即整份拒绝**,响应里给出**前若干条**失败原因(带行号),让用户能修文件。响应形状:

```json
{ "error": { "code": "IMPORT_INVALID", "message": "第 12 行:amount must be a positive number." } }
```

**缺失的分类/账户**:不自动创建(会静默污染基础数据),而是**明确失败**并指出是哪个名字。用户应先建好分类再导入。这是"明确"而非"静默丢弃"。

## 5. 决策四:UI 不提供恢复

**结论:不提供。**

`restoreBackup` 的既有契约是**必须停服**(`cli-db.ts:284`),否则会把数据库从运行中的进程底下换掉。而 UI 里的"恢复"按钮恰恰运行在那个进程里——它无法停掉自己。任何在 UI 内实现的恢复都必然是"热替换数据库文件",而那正是这条护栏要防的事:WAL 模式下替换文件会让连接持有旧的 inode,后续写入落到已删除的文件上。

因此界面只做三件事:列备份、触发备份、**给出可复制的命令行恢复指引**。这个取舍写进 spec。

## 6. 后端设计

### 6.1 新端点(`routes/portability.ts`)

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/export/transactions.csv` | 账单 CSV,`Content-Disposition: attachment` |
| GET | `/api/v1/export/salaries.csv` | 工资记录 + 分配明细 |
| GET | `/api/v1/export/recurring.csv` | 周期规则 + 到期项状态 |
| POST | `/api/v1/import/transactions` | 上传 CSV(正文为文本),返回统计 |
| GET | `/api/v1/backups` | 备份列表(文件名/大小/时间) |
| POST | `/api/v1/backups` | 触发一次备份,返回新文件 |

注册进 `app.ts` 的 `authModule.extraRoutes`。

**每张表一个文件**而不是打包:打包需要 zip 实现(又一个依赖),而三个 `.csv` 用户可以自己放进一个文件夹;且单个 CSV 能直接用 Excel 打开,这本来就是 R1 的目的。

**上传用文本正文而非 multipart**:`multipart/form-data` 需要 `@fastify/multipart`(依赖),而 CSV 本身是文本。前端用 `FileReader`/`File.text()` 读成字符串再 POST,`Content-Type: text/csv`。代价是文件大小受 Fastify 的 `bodyLimit` 限制——对个人账本足够,并在超限时返回明确错误。

**备份列表不返回绝对路径**:只返回文件名与元数据。宿主路径属于信息泄漏,对客户端也无用(它不能访问宿主文件系统)。

### 6.2 CSV 列定义(账单)

```
id,date,type,amount,category,account,note,tags,isRefund
```

- `date` = `YYYY-MM-DD`(本地日)
- `type` = `expense` / `income`(人类可读,而不是 0/1)
- `amount` = 元的十进制字符串,两位小数,非负;方向由 `type` + `isRefund` 决定
- `category` / `account` = **名称**而非 id(这是给人看的文件;而且导入按名称解析更可移植)
- `tags` = 用 `|` 连接(逗号在 CSV 里有特殊含义,不适合做分隔符)
- `isRefund` = `true` / `false`

**为什么导出名称而导入按名称解析**:id 是 UUID,对用户毫无意义;名称是用户能核对与修改的。导入时按名称查找分类/账户,找不到就明确失败(§4)。代价是重命名过的分类无法从旧文件导入——可接受,且错误信息会说明。

## 7. 前端

| 文件 | 内容 |
|---|---|
| `views/DataView.vue` | 导出区(三个下载按钮)+ 导入区(选文件 → 预览说明 → 确认 → 结果)+ 备份区(列表 + 触发 + 恢复指引) |
| `api/client.ts` | `portability` 命名空间;导出用 `window.location` 或 `<a download>` 触发,因为它是文件下载而非 JSON |
| `router/index.ts` | `/data` 一条路由,`meta.nav = 'settings'` |
| `views/SettingsView.vue` | 「数据导出与备份」入口 |

**下载如何触发**:导出端点是带会话 cookie 的 GET,浏览器直接导航会带上 cookie,因此用 `<a :href="..." download>` 即可,无需 `fetch` + Blob。这避免了把整个 CSV 先读进内存再触发下载。

**导入的确认步骤**:选中文件后先显示"将从 N 行中导入,重复的会被跳过",再确认。直接提交会让"点错了"变成一次不可撤销的操作(虽然全成或全不成提供了保护,但用户仍会困惑)。

## 8. Tradeoffs

| 选择 | 备选 | 为什么 |
|---|---|---|
| 自己写 CSV | 引入 `csv-parse` / `papaparse` | 只需转义与拆分两件事;项目的既定取向是不为小功能加依赖 |
| UTF-8 + BOM | 纯 UTF-8 | 无 BOM 时 Windows Excel 会用本地代码页解析,中文乱码。有 BOM 的代价是某些工具会把它当成内容——但目标是 Excel |
| 去重键用 `id` | 日期+金额+备注 | 自然键会误判合法的重复消费并丢数据;丢数据是这里最不可接受的失败 |
| 名称解析分类/账户 | 导出 id | 人要看这个文件;id 无法核对。找不到名称时明确失败而非猜测 |
| 全成或全不成 | 逐行部分提交 | 失败来源几乎总是"整份文件不对";部分成功要求 UI 表达难以理解的中间态 |
| 三张表三个文件 | 打包 zip | zip 需要实现(依赖);单文件可直接用 Excel 打开,正是目的 |
| 文本正文上传 | `multipart/form-data` | 少一个依赖;CSV 本就是文本 |
| UI 不做恢复 | UI 内恢复 | 恢复必须停服;UI 跑在那个进程里,热替换数据库文件正是护栏要防的事 |
| 备份列表只给文件名 | 返回绝对路径 | 宿主路径是信息泄漏,且客户端用不到 |

## 9. 兼容性与迁移

- **无 schema 变更**,无迁移。
- **既有 API 全部不变**;纯新增端点与页面。
- **导出不含已删除的账单**:软删除的行不出现在导出里,与账单列表口径一致。周期到期项导出其状态,便于核对"哪些期已处理"。
- **回滚**:纯新增文件 + 路由注册一处 + 前端页面,可整体 revert。
- **e2e 基线无需改动**:本任务的端点不写业务数据(导入写 `transactions`,而基线已清该表)。但 `e2e-portability` 会创建**备份文件**在 `DATA_DIR/backups`,基线不清那个目录——套件自己负责不要断言"目录里只有 N 个文件"。

## 10. 验证方案

| 层次 | 验证 | 对应 AC |
|---|---|---|
| `shared` 单测(csv) | 转义:逗号、引号、换行、前后空格;解析:引号字段内的逗号与换行、双引号转义、CRLF/LF 混用、结尾无换行、空字段 | AC3 |
| 服务层单测 | 导出→导入往返后**条数与净支出一致**;重复导入幂等;金额非法/缺列/未知分类各自的错误 | AC2, AC4–AC7 |
| 服务层单测 | 导入前后既有账单的 id/金额/备注逐字段不变 | AC8 |
| e2e(`e2e-portability.mjs`) | 真实 HTTP 往返:导出下载 → 导入 → 条数与合计;二次导入跳过;错误文件 400;备份列表与触发 | AC1–AC10 |
| 浏览器实测(`render-data.mjs`) | 页面渲染、文件选择控件与按钮 ≥ 44px、375px 无溢出、无备份时的空状态 | AC12 |
| 人工/工具 | **实测 Excel 可读**(导出文件带 BOM,用脚本断言前三个字节是 `EF BB BF`) | AC1 |
| 全量 | 既有单测 + 全部容器 e2e 零回归 | AC13 |
