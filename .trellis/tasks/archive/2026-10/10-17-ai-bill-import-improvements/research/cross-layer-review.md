## Findings requiring parent routing

### P1 — Review accepts stale persisted `viewRevision` without comparing the current live view
- Server GET rows/categories return `batch.view_revision` stored on the batch (`packages/server/src/services/import-batch-service.ts:1138-1145,1182-1187`); it is recomputed during create/analysis/file refresh, not when a category or transaction changes elsewhere (`:938-945`). Review first validates against stored row eligibility/categories, then checks only `batch.view_revision !== input.viewRevision` (`:2141-2152`). It later computes a fresh `liveViewRevision` and stores/returns it (`:2153-2165`) but never checks that fresh live value against the client’s read revision.
- Repro: GET batch/rows/categories with revision R; before POST review, add the row’s ledger ID to transactions or mutate the active category catalogue via an independent normal write; POST review with R. The persisted batch revision can still be R, so review can mint a token/summary against a view the client did not actually read. Confirm may later detect staleness, but the requested rebase contract requires the review attempt itself to reject and ask for a fresh read, rather than authorizing a different view under the stale screen.
- This also means separately fetched rows/categories may all report one identical but stale revision after live catalogue/ledger changes; equality across response strings alone is not sufficient unless the server computes/checks the live revision.
- Route to backend owner: compute current live view under the review transaction and require it to match the supplied revision (with a defined explicit rebase/read path); ensure validation uses the same fresh eligibility/catalog snapshot. Do not self-fix in this review.

### P1 — Server-issued review summary is parsed but its selected-row details are never shown
- Server actually returns `summary.selectedRows[]` with `itemId/type/amountCents/categoryId/suggestionId/note`; new/reuse category plans include names, types and selected-row counts (`packages/server/src/services/import-batch-service.ts:2396-2421,2423-2458`). Kotlin DTOs deserialize these arrays (`AssistantBatchModels.kt:617-647,649-724`).
- The review bottom sheet renders only totals and **counts** of categories (`AssistantBatchImportWorkspace.kt:1313-1353`). It never iterates `sum.selectedRows`, `sum.categoriesToCreate` or `sum.categoriesToReuse`; the category row renders only “N 个”, not the proposed names/type/associated count. It also does not render the selected rows’ notes. Further, server emits `note=null` for rows without an override (`import-batch-service.ts:2414-2421`), so the response alone does not contain the source note for those rows.
- Repro: select multiple rows with different notes/categories and one proposed category; tap “审核并核对金额”. The final modal shows selected count/totals and number of categories, but not which transactions, notes or category names/types are about to be written. This contradicts the frozen summary requirement to expose the financial summary and rows/categories before final confirmation; a user cannot verify the actual selected assignments at the confirmation point.
- Route to Android UI owner and backend owner if the review DTO must carry resolved full notes; UI can also join `selectedRows.itemId` against the already-loaded rows and local note overrides, but must display the full resolved data, not merely counts.

### P1 — `loadFullBatch` accepts mixed analysis/view snapshots across multiple HTTP requests
- It loads batch once, then categories, then up to five row pages, but only passes `b.version` as `includeVersion`; it updates `viewRevision` from each response without checking that `version`, `analysisRevision` and `viewRevision` match the initial batch and one another (`AssistantBatchImportWorkspace.kt:123-154`).
- Server emits those revision fields on each response (`import-batch-service.ts:1138-1145,1182-1187`), but `includeVersion` validates **only batch version** (`:1115-1119,1150-1155`). Analysis changes independently of file version. Thus an analysis can finish between categories/page requests: suggestions can be revision N while rows/page data are revision N+1, and the client commits this mixed collection to UI. Later review may use `currentBatch.analysis.analysisRevision` and stale assignments, leading to wrong display or a 409 rather than a coherent refresh.
- Repro: begin a batch load while analysis is running; let analysis complete between categories and row-page HTTP calls. Observe the UI uses `catsResp.items` from one revision with row AI fields from another; no consistency guard/retry exists. Compare all response revision triples locally and restart full load if any differ. The same guard should cover a `viewRevision` change between category and row snapshots.
- Route to Android owner; if desired protocol-level snapshot fencing needs stronger server support than response comparison, parent should decide. Do not infer consistency from `version` alone.

### P2 — Kotlin “strict” numeric readers silently truncate fractional JSON numbers
- `optIntFact`/`optLongFact` accept any `Number` then call `toInt()`/`toLong()` (`AssistantBatchModels.kt:11-28`); nullable row-count reader does the same (`:31-38`). These are used for money, counts, versions, ordinals and timestamps, e.g. `amountCents` (`:345-355`) and response revisions (`:206-222`, `:387-405`).
- Repro with actual reader input `{"amountCents":123.9,"version":1.5}`: it becomes 123 cents/version 1 rather than rejecting malformed wire. This violates the requested strict reader/type/null contract and can silently alter financial values if a server response regresses. Require integral/range-safe values (and explicit nullable handling), fail closed on wrong type/fraction rather than defaulting core fields to zero.
- Route to Android DTO owner; existing fixture/helper tests do not establish malformed-wire rejection.

### P2 — Suggestion approval cannot resolve ambiguous candidates or rename proposals
- Frozen protocol §7 / PRD P3 requires a user to choose among same-name active candidates or rename the proposed category; never auto-select the first candidate.
- Suggestion panel uses `sug.candidates.firstOrNull { it.isLeaf }` and the “复用” action immediately approves that candidate (`AssistantBatchImportWorkspace.kt:943-979`); the “新建” action always uses `sug.name` unchanged (`:987-996`). There is no proposal-name editor or candidate chooser. Server candidates are all exact name/type/parent matches (`packages/server/src/services/import-batch-service.ts:1158-1178`), and multiple same-name reuse candidates require explicit `reuseCategoryId` (`:2365-2374`).
- Repro: seed two active same-name/type/parent leaves for a suggestion; open category suggestions and tap “复用”. Client picks `firstOrNull` without presenting which choice is being approved; no rename path exists. For suggestion whose proposed name conflicts ambiguously, “新建” can proceed to server rejection rather than letting user resolve it. Per-row editor does list all same-type leaves (`AssistantBatchImportWorkspace.kt:544-571`), so user can route around by changing each row to an existing category, but this does not satisfy proposal-level approval/rename and associated rows flow.
- Route to Android owner; expose all candidates distinctly and an editable name/type/parent decision; preserve explicit approval gesture.

### P2 — AI `include: null` is coerced to `false`, erasing server’s “no recommendation” state
- Server row DTO explicitly allows `include: boolean | null` (`packages/server/src/services/import-batch-types.ts`, `ImportBatchAiDto`); Android models it as non-null `Boolean` and uses `optBoolean(..., false)` (`AssistantBatchModels.kt:274-290`).
- Repro with server response `ai:{status:"none",include:null,...}`: Kotlin represents it identically to an explicit AI exclusion. `loadFullBatch` default selection checks `row.ai?.include == true || row.ai == null` (`AssistantBatchImportWorkspace.kt:162-174`), while the DTO creates an `ai` object for the response. Unanalysed/failed rows with null recommendation therefore silently default unselected, and UI cannot distinguish “AI said exclude” from “no advice”. Manual selection remains possible, but this is a wire-semantic loss and likely incorrect default/review affordance.
- Route to Android DTO/UI owner; keep nullable include and choose explicit UX for no recommendation.

### P2 — 401 handling is omitted in batch polling and file mutation UI paths
- Analysis polling swallows any non-cancellation exception and exits (`AssistantBatchImportWorkspace.kt:210-225`) without invoking `onAuthExpired`; replace/remove catches all exceptions into a local error banner (`:260-294`, `:713-740`) and likewise do not route `AuthExpiredException` to the session expiry callback. Other batch flows explicitly do so, e.g. confirm (`:1390-1392`).
- Repro: expire session during running-analysis polling or while replacing/removing a failed file. Instead of entering the established re-auth/expired-session path, polling silently stops or mutation reports an ordinary local failure. Route to Android owner.

### P2 — Analysis polling response bypasses request/session gate and may overwrite a newer workspace batch
- Main batch/category/row loading uses `AssistantRequestGate` (`AssistantBatchImportWorkspace.kt:118-154`), but polling directly assigns `batch = updated` with no ticket/scope validation (`:209-220`). `LaunchedEffect` is keyed only by analysis state, not batch/conversation/revision (`:210`); an old GET response can arrive after workspace/session switch and overwrite current `batch`, while other collections belong to another batch.
- Repro: while batch A is `running`, start a poll; switch workspace/conversation or reopen batch B before A's GET resolves; return A's response. It assigns stale A without checking conversation/batch identity. Route to Android owner: gate by conversationId+batchId+analysisRevision and invalidate/cancel on scope change; do not assign stale responses.

## Verified closure / no stale repeats
- Category row editor lists all active same-type categories, not just AI candidates (`AssistantBatchImportWorkspace.kt:544-571`); selected-row assignment is submitted explicitly (`:1229-1262`).
- Suggestion auto-approval is absent; explicit “复用/新建/撤回” controls exist (`:966-1013`), and stale suggestions/approvals are pruned on reload (`:177-188`). I do not repeat the former auto-approval finding.
- Positive ignored-row eligibility is represented in Android `isEligible` without status-string hard locks (`AssistantBatchModels.kt:323-327`); this report does not re-report the earlier eligibility issue.
- API DTO field names/types for batch, rows, categories, review, mutation and duplicate response were read against actual route/service shapes. Confirm response `{batch,result}` is unwrapped by the repository; uncertain-outcome recovery GETs the same batch (`AssistantRepository.kt:283-305`; workspace `:1380-1403`). Duplicate endpoint DTO has the expected `source.itemId` shape.
- `GET categories` carries server suggestion-wide `relatedItemCount` only; selected-row counts are computed in POST review validation (`import-batch-service.ts:1165-1172,2344-2348`). Client suggestion panel separately counts selected assignments (`AssistantBatchImportWorkspace.kt:923-927`); do not derive selected counts from categories GET.
- Category suggestions UI uses only the first exact-match candidate for “复用” and offers no rename UI (`AssistantBatchImportWorkspace.kt:943-1002`), although row editor permits selecting any existing same-type leaf (`:544-571`). This violates proposal-level candidate choice/name resolution in protocol §7; assigned as a distinct P2 above.
