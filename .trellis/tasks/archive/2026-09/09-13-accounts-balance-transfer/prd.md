# 账户余额与转账

> 父任务。来自用户 2026-09-13 的需求：「目前账户的作用还不明确，我给账户填写了初始资金。那么我记工资的时候就需要一个账户来接受。然后就是首页需要展示总余额」。用户已确认：**一起做转账**。

## Goal

让「账户」从一个只被存下来的字段，变成**真正持有钱的地方**：

- 工资能指定打进哪个账户；
- 每个账户有余额，首页顶上能看到总余额；
- 钱可以在账户之间搬（转账），且**不会**被当成收入或支出。

用户价值：现在 3 个账户的 ¥6,281.32 初始资金被系统记下了却从不显示、从不参与任何计算。用户没法回答「我还有多少钱」「上个月工资进哪张卡了」「这笔支出从哪个账户出的」。

## Background

### 仓库现状（已核对，含线上库实测）

| 能力 | 现状 | 证据 |
|---|---|---|
| 账户表 | ✅ 有，含 `initial_balance_cents` | `db/migrations/001-init.ts:54-63` |
| 账户 CRUD | ✅ 有 | `routes/master-data.ts:110-142`，`services/master-data-service.ts:258-390` |

| **余额计算** | ❌ **完全没有** | 全仓 `initial_balance_cents` 只出现在 seed / DTO / 校验 / 写库四处，**没有任何计算读取它** |
| **工资挂账户** | ❌ `salary_records` 无 `account_id` | `001-init.ts:94-101`，`services/salary-service.ts:235-249` |
| **账户间转账** | ❌ 没有 | 全仓无 transfer 相关表/代码 |

线上库（`jz.yansuu1.com`，2026-09-13 实测）：

```
accounts:  支付宝 ¥589.35(builtin，用户改名) / 微信 ¥49.12 / 上海银行 ¥5,642.85
           合计 ¥6,281.32
transactions: 0 笔    salary_records: 0 笔    budget_allocations: 0 行
users: 1
```

**结论：账户是半成品——被完整地存、校验、返回、可编辑，但没有任何一行代码读它来算钱。** 线上 0 笔账单、0 笔工资，因此本次迁移不触碰任何历史业务数据。

### 必须遵守的既有硬约束

- **金额整数分、时间 epoch 毫秒**；无 `REAL`。
- **不存物化余额**：`spec/backend/database-guidelines.md:105-109` 明确禁止 `remaining_cents` / `carryover_pool_cents` 类列，并有测试断言其不存在。余额必须是实时派生。
- **会计口径在 `@jizhang/shared`，服务端只搬行**；前端只渲染、不算钱。
- **退款是负支出，永不计收入**（`types.ts:156-173`）。余额必须复用这两个函数，不得重写退款规则。
- **迁移只增不改**；新列必须有 `DEFAULT`；新迁移追加到 `migrate.ts` 的 `MIGRATIONS` 数组末尾。
- **新增受保护路由必须进 `app.ts` 的 `extraRoutes`**（`app.ts:149-164`）——这是 `spec/backend/index.md:46-48` 记录的最贵的坑：hook 与路由不在同一 plugin 里会静默失守，且单测全绿。
- **底部导航已满 6 格**（首页/账单/预算/记一笔/统计/我的），不得再加一级入口（`spec/frontend/index.md:122-133`）。

## 本父任务拥有的跨子任务验收标准

- [ ] **PAC1 总余额自洽**：首页总余额 = 各账户余额之和 = `Σ初始资金 + Σ收入账单 − Σ净支出账单 + Σ工资 + Σ转入 − Σ转出`。用一组同时含**支出、收入、退款、工资、转账**的数据端到端断言，而不是分别断言。
- [ ] **PAC2 转账对会计口径零影响**：同一份数据，记一笔转账前后，**预算总分配/总已用/结转池、本月收入、本月净支出、分类占比**逐字节不变。
- [ ] **PAC3 口径唯一**：退款在「余额」上表现为**加钱**、在「收入」上表现为**不计**，两条规则同时成立且都来自 `types.ts` 的同一对函数。
- [ ] **PAC4 账户下钻一致**：按账户筛选的账单列表里的行，与该账户余额的构成明细一致（收入/支出/工资落点）。
- [ ] **PAC5 全量门禁**：`py`/`pnpm build`（含 4 个静态审计）、`pnpm test`、`pnpm lint`、`pnpm typecheck`、12 个容器 e2e、7 个浏览器渲染套件全部通过。

## Out of Scope

- **转账不进回收站**：沿用既有范围决定「回收站只覆盖账单」（`spec/backend/database-guidelines.md:93-96`）。转账为软删除、无恢复 UI。**已知代价**：误删一笔转账只能靠数据库备份找回。
- **转账不进 CSV 导出/导入**：`PortabilityService` 目前只导出账单。CSV 保持为「账单交换格式」，整库备份（`cli.js backup`）覆盖转账。**已知代价**：只靠 CSV 备份的用户会丢转账。列为后续候选。
- **转账不进账单列表**：`transactions` 表与账单页保持完全不动，这是「预算引擎零改动」的前提。
- 信用卡的负债建模：不做特殊处理，沿用现有「初始余额可为负」的校验（`master-data-service.ts:560`，`test/master-data.test.ts:333` 已断言 −50_000 合法），总额自然得到净资产。
- 账户余额的历史曲线 / 按周期余额。

## Risks

| 风险 | 缓解 |
|---|---|
| 余额让预算或统计跟着变（最危险） | 转账独立成表，`budget-engine.ts` **一行不改**；PAC2 用「转账前后逐字节不变」钉死 |
| 工资 `account_id` 为必填，破坏既有调用 | 线上 0 笔工资；单测/e2e 同步更新；无外部调用方 |
| 新路由忘记进 `extraRoutes` 导致无鉴权 | `implement.md` 显式列为风险点，并加「无 cookie → 401」断言 |
| 首页数字与账单列表对不上（未来日期口径） | 余额**不做日期过滤**，与账单列表同口径；写进 design 并加测试注释 |
| 首页多一张卡挤掉「最近账单」 | 资产卡紧凑（总余额一行 + 每账户一行），列入渲染回归断言 |
