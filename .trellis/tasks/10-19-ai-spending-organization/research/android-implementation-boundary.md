## Scope and non-scope

The later Android implementation should add a dedicated, full-range organization review flow while reusing existing Assistant session/request isolation, tag/category/template display vocabulary, repository transport, and single explicit confirmation affordance where those contracts fit. It must not implement or infer the backend protocol before the backend-owned contract is frozen. The relevant APIs and DTOs below are **contract items to agree**, not a proposal that Android may define their paths or wire shape.

Do not reuse the generic assistant operation confirmation route if it results in a second confirmation after a review workspace's final button. For this feature, one review card's explicit final confirmation is the one authorization action. Review, loading, retrying analysis, and viewing a card are read-only. Undo is a separate user action only after a known successful apply.

### Tag wire/string compatibility: current facts and minimum client behavior

Current observed contract in Android is a legacy name list: `GET /api/v1/tags` is consumed as `{items:[{name,...}]}` (`ManageTab.kt:189`, `TransactionsTab.kt:182-184`); the transaction filter query sends a `tag` label (`TransactionsTab.kt:143`); transactions expose `tags` as strings (`TransactionsTab.kt:655`, `TransactionEditSheet.kt:196-198,313,520`). `AdminRepository.kt:77-86` explicitly describes name identity and name-based rename/delete. There is no existing Android stable tag identity or hierarchy DTO.

After backend contract freeze, Android should:

- Parse optional stable ID, parent ID, display name, and any explicit compatibility/legacy-name field as a new additive DTO; do not conflate category `id`/`parentId` fields with tag identity.
- Retain the old name-only reader path. If the response has no hierarchy fields, render current flat names unchanged; do not fail or fabricate hierarchy.
- Send only the contract-designated stable ID for newly supported hierarchy-aware filters/associations, while preserving the existing name-array transaction field for legacy readers/writers if that remains the negotiated compatibility contract.
- Keep name fallback display available for unknown/deleted legacy references. Never resolve a legacy string to one of multiple same-label branch tags by guess; represent ambiguous names as legacy/ambiguous until an explicit server resolution exists.
- Use backend-defined collision disambiguation for duplicate labels across branches. UI may display path such as parent › child only if the API gives an unambiguous stable identity/path; labels are never identifiers.
- Let the server implement parent filter semantics and transaction deduplication; Android consumes the already-filtered list/count once.

These are minimum client safeguards, not a claim that the backend’s eventual tag DTO/storage design is decided here.

## Required Android UI phases (proposal for later implementation)

1. **Choose scope:** Assistant entry “消费整理”; month shortcuts plus custom inclusive start/end date picker; show the selected calendar dates as user-entered. Obtain authoritative interpreted timezone/boundaries/count from backend; Android does not derive the backend epoch interval from device timezone.
2. **Analyze:** Start a uniquely identified run. Show truthful completed/total batches and records only from authoritative progress. Retry is an explicit new/approved analysis retry for the same selected scope; no client-side sampled fallback. On over-cap, failure, cancellation, stale run, or 401 show terminal status and no actionable partial card. Keep old run results from appearing as the new run.
3. **Review:** Publish only after backend says the entire accepted run finished successfully. Show exact scope/timezone/count and each affected transaction identity, category before/after, tag associations before/after, proposed new tag/parent-child structure, and separately marked note suggestion (never replace source note). Structure-only and module+budget proposals are separate/clear action choices. For new template show the whole solution; for explicitly selected existing template show all affected ratios before/after. Spend evidence is not a budget amount/current allocation. Keep candidate changes editable only if backend contract supports re-review/revision; any edit invalidates a stale review token/snapshot before confirmation.
4. **Single confirmation:** One final button authorizes exactly the displayed review. Do not show generic `AssistantConfirmationScreen` afterward or initiate another confirm dialog. Back/cancel from review has no mutation. Disable duplicate submissions while in flight and preserve the operation identity.
5. **Known outcome and uncertainty:** On success show authoritative operation result and enable conditional undo. On timeout/connection loss/unknown write outcome do **not** create a new key or automatically resend apply/undo. Fetch/reconcile the same run/card/operation using a frozen GET/status contract; until GET establishes terminal success/failure, keep action locked and show “result pending verification”. A stable known failure can expose an explicit retry only when backend declares retry-safe/idempotent semantics and the same operation identity is retained.
6. **Undo:** Display a distinct undo action for a known applied operation. If conditional undo reports a conflict, show conflict and do not claim partial restoration. No client-side deletion of newly-created tag entities; server owns reference checks.
7. **Template scope:** Default action is propose/create a **new** template. Existing-template update requires an explicit selector and complete diff. Structure-only changes create/use categories only as in frozen server contract and do not alter template ratios. No action calls the current-cycle template endpoint or touches historical/current allocations.

## Minimum backend contract checklist for Android handoff (must be frozen by backend owner)

This section intentionally does not name or invent endpoint paths, request fields, status codes, error codes, or DTO schemas. Backend owner must provide concrete examples and freeze these before Android implementation begins.

- [ ] Authenticated request to start analysis identifies month shortcut OR inclusive custom dates, never both; server response supplies canonical inclusive interval interpretation, server calendar timezone, eligible count, accepted limit/cap outcome, and stable run identity.
- [ ] Progress/status read exposes a monotonic run/revision identity, total/finished batches and records, and terminal state. It distinguishes queued/running/complete/failed/cancelled/over-cap/stale as agreed; only complete runs can become actionable.
- [ ] Accepted run reads every eligible live transaction by transaction date, with no sample/truncation; 25-record chunks and 500 maximum are currently provisional proposals only. Backend must state the calibrated/frozen accepted size and batch shape. A failure at any batch yields no partial review card.
- [ ] Retry/cancel behavior is explicit: identify whether cancel interrupts only client polling or provider work; define safe reanalysis identity and whether a failed attempt can be retried without duplicating durable effects. Analysis itself performs no write to ledger/master/template.
- [ ] Completed review response contains exact scope/timezone/count/coverage, stable run/review/version/fingerprint/expiry identity as applicable, all transaction before/after category and tag associations, separate note suggestions, new-tag hierarchy proposals, structure-only vs module+budget proposal type, and complete template proposal/diff data. It contains no unsupported or ambiguous identity mapping.
- [ ] Template proposal contract covers full 100% proposed ratio solution; new template shows every module; existing template can only be selected explicitly and returns every affected module’s before/after ratio. Expense evidence field semantics are frozen by backend/shared-engine owner and cannot be inferred/recomputed on Android. Actual spending evidence never supplies a budget amount or current-cycle allocation.
- [ ] Exactly one explicit apply/confirm call applies exactly the displayed reviewed projection. Provide idempotency/replay contract (same identity/key behavior, mismatched payload behavior), stale-preview conflict behavior, and whether a successful retry returns the original operation result.
- [ ] Apply response exposes a stable operation identity and terminal outcome sufficient to reconcile an unknown network write through GET without creating a new key. Apply atomically changes only approved transaction category/tag associations, approved new tag entities, and optional future-use template; original notes and amount/type/account/date/refund fields remain unchanged.
- [ ] Conditional undo contract says which operation-owned fields are compared/restored, returns a conflict without partial undo, protects new entities with references outside the operation, and exposes an authoritative operation/undo GET recovery path after network uncertainty.
- [ ] Hierarchical tag wire compatibility specifies stable IDs, display names, parent IDs/path, exact representation of legacy name arrays, handling of same-name tags in different branches, old Android client round-trip behavior, rename semantics, and fallback for old name-only response/readers. It does not require Android to treat a label as a unique ID.
- [ ] Parent tag filtering explicitly includes direct assignments + child assignments and deduplicates transaction rows/counts server-side; child filter is exact child; query uses stable identifiers once hierarchy-aware Android support is enabled.
- [ ] DTO examples include old response compatibility fixture and new hierarchy response fixture; date boundary/timezone/DST examples; complete/incomplete/failure progress; stale conflicts; safe error shape/status; 401/session expiry; apply/undo timeout GET recovery; both template proposal types.
