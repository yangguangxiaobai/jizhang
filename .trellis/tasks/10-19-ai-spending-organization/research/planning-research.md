# Planning Research — AI Spending Organization

Date: 2026-10-19. Source inspection only; no runtime, Provider, database, deployment or device verification was performed. Line references below are in the current working tree and should be refreshed before implementation.

## Confirmed repository facts

1. **Current AI organization path is not the requested workflow.** `packages/server/src/services/ai-organization-service.ts:24-28` defines `MAX_SEMANTIC_TRANSACTIONS = 200`; `:409-427` loads all live transaction tags for deterministic merge planning but semantic input is only the most recent 200 live transactions, ordered by date/update. `packages/server/src/routes/ai.ts:78-89` exposes preview/apply/undo without a date-range body contract. Existing action kinds are `tag-merge | category-merge` (`packages/server/src/services/ai-types.ts:180-203`); semantic reclassification/new-category outputs remain recommendations. Apply consumes the deterministic merge plans (`ai-organization-service.ts:1060-1113`).
2. **Existing audit and undo are useful but insufficient as-is.** Migration 008 constrains audit kinds to merge operations (`packages/server/src/db/migrations/008-ai-organization-audit.ts:1-21`). Existing undo checks current fields against the apply after-state and conflicts rather than overwriting later changes (`ai-organization-service.ts:1123-1164`). New action types and projection/audit coverage are required.
3. **Legacy tags have names, not entity IDs.** `packages/server/src/db/migrations/001-init.ts:65-83` defines `tags_json` with a name-array comment. `packages/server/src/services/tags.ts:9-19,25-59` confirms name identity, trimming/deduplication, 32 characters per name and 20 tags per transaction. `master-data-service.ts:500-505,547-552` derives current tag vocabulary from live transaction JSON and rewrites that JSON for rename/delete. A tag hierarchy migration must preserve this representation or provide a proven dual-read/write compatibility layer.
4. **Category hierarchy creates a bookability compatibility hazard.** Migration 007 only adds `categories.parent_id` and an index (`packages/server/src/db/migrations/007-category-hierarchy.ts`). `MasterDataService.requireParentId` enforces an active expense parent with no parent of its own (`master-data-service.ts:~130-177`); `TransactionService` rejects recording directly to a parent category (`transaction-service.ts:~330-350`). Existing historical transactions can reference an old category that later becomes a parent. Do not create children under referenced categories without an explicit preservation rule and tests.
5. **Template semantics are specific and reusable.** `packages/server/src/services/template-service.ts:~15-24,~65-115,~150-220` validates nonempty modules, unique category IDs, positive finite ratios summing to 1 within `RATIO_SUM_TOLERANCE`, and rejects selecting parent+child together. Create/update mutate only `budget_templates`; salary allocations are separate snapshots. Android README §4.10 (M02.02–M02.06) documents current template editing and explicit current-cycle application; this task must not invoke the latter.
6. **Shared financial aggregation must remain authoritative.** `packages/server/src/services/stats-service.ts:~90-145` loads live transactions by `[from,to)` and maps to the shared transaction shape; `:175-195` uses `expenseContribution`. Existing contract differentiates refund income from expense. Template evidence should reuse existing/shared aggregation semantics instead of creating a second formula.
7. **Date and zone conventions exist but don't fully settle this feature.** Stats requests use epoch boundaries `[from,to)` (`stats-service.ts:~96-120`); assistant monthly evaluation captures a server-local date/time boundary (`.trellis/spec/backend/ai-provider.md`, “On-demand current-month evaluations”). Android formats epoch dates by device timezone, while Android README P035 explicitly notes the client/server timezone difference. Proposed feature must return server-local interpreted date labels and exact epoch bounds; do not derive authoritative boundaries on Android.
8. **Existing batch mechanisms are precedents, not a safety benchmark for this feature.** Assistant bill-import analysis runs sequential chunks of 25 (`packages/server/src/services/assistant-orchestrator.ts:149-160`); merged-import limits are `MERGED_MAX_ITEMS=500`, `MERGED_MAX_TOTAL_RAW_ROWS=5000` and distinct byte limits (`packages/server/src/services/import-batch-types.ts:17-40`). Generic organization has a 200-row semantic sample. These numbers have different payloads, workflows and acceptance and cannot prove an AI organization cap safe.
9. **Provider and streaming bounds.** Provider responses are capped at 2 MiB (`packages/server/src/services/ai-provider-service.ts:20,~700-720`); assistant stream envelopes/replay are also bounded to 2 MiB (`assistant-stream-types.ts:16-29`). This controls transport memory but does not establish acceptable total run latency, provider cost, database memory or partial-result behavior.
10. **Migration pattern.** Latest migration at research time is 012; migration runner imports and appends numbered TypeScript migrations in `packages/server/src/db/migrate.ts:15-49`. Each migration runs in its own transaction, and an upgrade snapshot uses `VACUUM INTO` (`database-guidelines.md:33-57`, `migrate.ts:~125-165`). Do not alter shipped migrations.
11. **Assistant card authorization is established, but not a substitute for a purpose-built range workflow.** Provider prompt says writes only prepare and never perform a write until separate user confirmation (`ai-provider-service.ts` assistant system prompt); `assistant-tool-registry.ts:392-400` separates read/prepare and `:841-873` routes writes through prepared actions. Existing orchestrator handles provider-selected tools and import batches but does not guarantee natural-language tool selection (`artifacts/ai-organization-capability-audit-20261019.md`).
12. **Android evidence baseline.** `clients/android/README.md` §4.6, §4.9, §4.10 and §6 record flat single-tag filtering, tag management by derived names, template semantics, generic assistant cards, and a source/local-test baseline of 156 unit tests. This baseline is not feature evidence and not physical-device/provider verification. `clients/android/ui-redesign/README.md` is a plan, not implementation evidence.

## Numeric capacity proposal (provisional, not validated)

A 500-eligible-transaction analysis cap with sequential batches of 25 is a **technical proposal for investigation only**. It is not a user-approved product limit, benchmark result, or safe-capacity claim. Existing provider-import chunks and merged-import ceilings are from different workflows and do not establish a valid capacity for this feature. Keep this proposal out of acceptance language and do not implement it as a fixed contract absent representative characterization and explicit review.

Evidence required before selecting any cap: synthetic tests at 1/25/26/200/500/501 records; representative bounded-note/tag payload-size tests; provider-stub request/response limits; timeout and failure injection at every batch boundary; measured memory/latency/request counts; and confirmation that any failed chunk discards all actionable output. If project owners require actual-export measurements, source-only synthetic benchmarks do not satisfy that gate. The chosen limit must be feature-scoped; never silently lower coverage or truncate.

## Open implementation research tasks

- Decide additive tag identity schema and dual compatibility for legacy Android/web clients that still write name arrays; inspect all transaction read/write/update/export/import routes before choosing canonical storage. Decide identity treatment for same label under different parents, case/Unicode normalization, renamed entities, soft-deleted tags and per-transaction maximum.
- Decide how category structure creation handles a proposed parent already directly referenced by transactions and whether the “module” must be a category node or a separate concept. Current category rules forbid new bill entry against a parent; preserve that invariant.
- Decide persistence/retention/privacy/access/deletion lifecycle for separate AI note suggestions (source note remains immutable). Minimize note retention and avoid storing original notes in audit/provider history.
- Define run snapshot storage, expiration/cleanup, progress state and how to reuse or avoid assistant generation infrastructure; define cancellation/retry and exactly-once/idempotent confirmation behavior.
- Verify how actual-spending evidence maps to proposed modules under the shared budget engine's expense/refund semantics. The ratio scope is resolved to complete template modules totaling 100%, but no new gross-expense denominator or refund-offset formula was approved; do not invent one.
- Specify parent tag filter query shape/indexing and deduplicated result count; tests must include a transaction with direct parent plus a child association and multiple children.
