# 回收站 — 需求

> 父任务:`09-11-roadmap-2`,对应 R9。第二阶段「块一」中与 `09-11-home-dashboard` 并列的另一半。

## Goal

给软删除的账单一个入口:能看到删掉了什么、能恢复、能彻底删除。

用户价值有两面:

- **误删可救**。现在删除是静默且不可逆的——前端没有入口能看到已删除的账单,用户只能看着它消失。
- **数据真的能被清掉**。反过来,软删除意味着"删了"的行**永远留在库里**。没有彻底删除,账本只会单向膨胀,而这正是一份财务记录里最不该出现的东西。

## Background

### 仓库现状(已核对,含 `file:line`)

| 能力 | 现状 | 证据 |
|---|---|---|
| 软删除 | ✅ 已有 | `transaction-service.ts:345-351` `softDelete()` 置 `deleted = 1` 并 bump `updated_at` |
| 恢复 | ✅ 已有 service 方法,**但没有路由** | `transaction-service.ts:353-361` `restore(id)` 返回 `TransactionDto`;注释写着 "Used by tests and the future trash view" |
| 物理删除 | ❌ **完全没有** | service 与路由中均无 `purge` |
| 列出已删除 | ⚠️ 只能拿到**混合**列表 | `list()` 在 `includeDeleted === true` 时**不加** `deleted = 0` 条件(`:390-392`),即返回"已删除 + 未删除"两部分 |
| 前端区分已删除行 | ❌ **不可能** | `TransactionDto`(`:45-56`)**不含 `deleted`**;`toDto`(`:58-71`)也不映射 `row.deleted` |
| 路由 | 只有软删除 | `routes/transactions.ts:129-135` 注册 `DELETE /api/v1/transactions/:id`,无 restore / purge |

**结论:前端今天无法实现回收站。** 不是因为缺 UI,而是因为**没有一条能确定性地拿到"仅已删除"记录的通路**——`includeDeleted=true` 返回混合数据,而 DTO 里没有可用来过滤的字段。这是本任务真正要解决的问题,比"写一个页面"重要。

### 参考项目行为(权威来源)

`lib/features/trash/trash_page.dart`(285 行):

- 列出全部已删除账单,支持**单条恢复**、**单条彻底删除**、**全部恢复**、**全部清空**
- 破坏性操作有二次确认对话框(`_confirm`)
- 操作进行中禁用按钮防重复提交(`_busy`)
- 删除时间用 `updatedAt` **代理**:账单在回收站期间不会被编辑,所以 `updatedAt` 恒等于删除时间(源码注释明说)
  - 本项目 `softDelete` 同样是 `UPDATE ... SET deleted = 1, updated_at = ?`,因此该代理在这里同样成立
- 它没有做"回收站自动过期清理"

### 必须遵守的既有硬约定

- **软删除是默认,物理删除是例外**。父任务不变量第 5 条要求业务表带 `deleted` 列、不做物理删除;本任务引入的 `purge` 是**唯一被明确授权的例外**(R9 要求"彻底删除"),因此它必须是显式的、有二次确认的、且只由用户动作触发。
- **前端只渲染,不算账**。恢复/彻底删除后,汇总数字必须重新从服务端取,而不是在前端加减。
- **金额整数分、时间 epoch 毫秒**;`updated_at` 作为删除时间代理时不得写成除服务端时钟外的其它来源。
- **44px 触摸目标 / 16px 输入字号 / 375px 无横向溢出**,由 `check-mobile.mjs` 在构建期强制。
- 新增能力必须有测试:单测驱动路由用 `app.inject()`,端到端接 `packages/server/scripts/` 的既有风格与 `resetToKnownState()` 基线。

## Requirements

### R1 后端:确定性地列出已删除账单

- 必须存在一条**只返回已删除账单**的通路,且调用方能判断"哪些行是已删除的"
- 排序按**删除时间倒序**(即 `updated_at` 倒序),因为回收站的语义是"最近删的排最前",而不是"账单日期最近的排最前"
- 必须带上限,不得无界返回;上限需在 design.md 定夺并说明

> 实现方式(给 `list` 加 `onlyDeleted` / 给 DTO 加 `deleted` / 新增 `/api/v1/trash`)在 design.md 定夺。R1 只约束**行为**:调用方能可靠地拿到"仅已删除"的集合。

### R2 后端:恢复

- 能恢复单条已删除账单
- 能批量恢复(参考项目的"全部恢复")
- 恢复后该账单重新参与账单列表、预算与统计的聚合
- **幂等性**:对一条未删除的账单调用恢复不得报错或损坏数据(见 design.md §幂等决策)

### R3 后端:彻底删除

- 能彻底删除单条已删除账单;物理删除该行
- 能批量彻底删除(参考项目的"全部清空")
- **只允许删除已处于软删除状态的行**:对一条**未删除**的账单直接彻底删除必须被拒绝。这是防止"误把正常账单抹掉"的关键护栏,不能省
- 彻底删除后,该账单不得再影响任何聚合,且任何接口都不应再返回它

### R4 前端:回收站页面

- 列出已删除账单,展示**金额、分类名、账单日期、删除时间**,收支/退款的显示口径与账单列表一致
- 单条**恢复**、单条**彻底删除**;每一条都必须有明确的二次确认,确认文案必须写清"不可撤销"
- **全部恢复**与**全部清空**两个批量动作;批量破坏性动作的确认文案必须给出将影响的条数
- 操作进行中禁用相关按钮,防重复提交
- 空回收站显示空状态,而不是空白页
- 操作后列表与计数立即反映真实状态

### R5 前端:入口

- 全局导航是 6 项,**不得再加 tab**(D12 已定,且 375px 下已验证 6 项刚好容纳)
- 回收站必须能从已登录界面到达,入口放在"我的"或"分类与账户"之下,并在 design.md 说明选择
- 进入回收站时底部导航的"我的"应处于高亮态(与既有 `meta.nav` 机制一致)

### R6 移动端与无障碍

- 全部可点击元素 ≥ 44px;破坏性按钮与恢复按钮必须视觉可区分,且**不能只靠颜色**区分(既有规范:不得仅以颜色传达状态)
- 页面在 375px 下无横向溢出
- 危险操作按钮使用 `--danger` 语义变量,不写死颜色(为 T16 深色模式留路)

## Acceptance Criteria

- [ ] AC1 删除一笔账单后,回收站能列出它,并显示金额、分类、账单日期与删除时间
- [ ] AC2 恢复后该账单回到账单列表,且预算页/统计页的金额回到删除前状态
- [ ] AC3 彻底删除后该账单永久消失:回收站不再列出,账单列表与任何聚合都不再受它影响
- [ ] AC4 对一条**未删除**的账单调用彻底删除接口被拒绝(不是静默成功)
- [ ] AC5 恢复一条**未删除**的账单不报错、不改变其状态(幂等)
- [ ] AC6 批量恢复把回收站清空,且所有账单回到账单列表
- [ ] AC7 批量彻底删除把回收站清空,且这些账单不再出现在任何接口响应中
- [ ] AC8 回收站按**删除时间倒序**,最近删除的排最前
- [ ] AC9 空回收站显示空状态,页面不空白、无报错
- [ ] AC10 回收站只返回已删除账单,绝不混入未删除账单(防回归:`includeDeleted` 语义不得被本任务破坏)
- [x] AC11 全部可点击元素 ≥ 44px,375px 下无横向溢出,构建期 `check-mobile.mjs` 与 `check-pwa.mjs` 通过 — 两个构建期审计 PASS;`render-trash.mjs` 实测 `scrollWidth=375`、无 <44px 控件、10 个可交互控件
- [x] AC12 既有 235 项单测与 266 项容器 e2e 全绿,且本任务新增能力均有对应测试 — 单测 **235 → 256**(新增 `test/trash.test.ts` 21 项);容器 e2e **266 → 327**(新增 `e2e-trash.mjs` 61 项);全部既有套件零回归

| AC | 证据 |

| AC2 | `e2e-trash`:恢复后回到 `3`;月度周期支出 `110000 → 95000 → 110000`,`modules` 的 JSON 在往返前后**完全相等** |

> **发现的真实缺陷(已修):** `restore` 原实现对**未删除**的账单也会执行
> `UPDATE ... SET deleted = 0, updated_at = now`,而 `updated_at` 是列表排序的次级键 —— 该行会**在列表中静默跳位**。已改为提前返回,并用单测把"`updatedAt` 不变"钉死。

## Out of Scope

- **回收站自动清理 / 保留期**(如"30 天后自动彻底删除")— 参考项目也没有;引入定时任务与 1核1G VPS 的约束冲突
- **分类/账户/模板等其它软删除实体的回收站 UI** — 它们在库中同样带 `deleted` 列,但本期只做账单;本限制必须写进 spec,否则会被误认为遗漏
- **撤销(undo)提示条** — 恢复通过回收站完成
- **删除原因 / 操作人 / 审计日志** — 单用户应用
- **跨设备同步删除**(D4/D7 已排除)
- **把回收站做成底部导航的第 7 个 tab** — D12 已定 6 项

## Technical Notes

- **`updated_at` 作为"删除时间"代理**:与参考项目 `trash_page.dart` 的注释一致。成立的前提是"已删除的账单不会被编辑";`restore` 也会 bump `updated_at`,所以恢复后再删除会得到新的删除时间,这也是正确行为。**恢复后该行的 `updated_at` 不再等于删除时间**,因此回收站不得把 `updated_at` 用于已恢复的行。
- **`purge` 与悬挂引用 —— 已核实:不存在。** `transactions` 表**没有任何入向外键**(`001-init.ts` 中唯一的 `REFERENCES` 是 `sessions -> users`),`budget_allocations` 指向 `salary_records` 而非账单。因此物理删除**无需级联清理**。
- **失败模式 —— 已决:单事务,全成或全不成。** `restoreAll` / `purgeAll` 各自包在一个 `db.transaction()` 内,返回受影响条数。单用户本地 SQLite 下部分失败几乎只可能来自程序错误,让调用方表达"3 成功 2 失败"没有收益。
- **路由必须在 `app.ts` 的 `authModule.extraRoutes` 数组内注册**,不能是同级 `app.register` —— 否则重演第一阶段"钩子与路由不在同一封装上下文 → 路由完全无鉴权、而 29 个单测全部通过"的事故。`test/trash.test.ts` 对五个端点逐个断言 401 作为防回归。
- **对未认证的 mutating 请求断言 401 时必须带 CSRF 头**,因为 CSRF 检查先于鉴权守卫(否则得到 403,证明的是 CSRF 而非会话)。这与 `test/budget.test.ts:660-662` 的既有做法一致。
- **无 body 的请求不得送 `Content-Type: application/json`**(否则 Fastify 在路由前返回 400 `FST_ERR_CTP_EMPTY_JSON_BODY`);e2e 用 `resetToKnownState()` 返回的 `csrfOnlyHeaders`。
- 新增前端页面走既有 `api/client.ts` 单一 JSON 边界,不在组件里直接 `fetch`。
- 新增 e2e 套件 `e2e-trash.mjs` 接入 `resetToKnownState()` 基线;该基线已 `DELETE FROM transactions`,因此天然清理回收站内容。
- 浏览器实测在 `packages/web/scripts/render-trash.mjs`,基于共享驱动 `scripts/lib/browser.mjs`(与首页共用同一套 44px / 375px / 离线定义)。
