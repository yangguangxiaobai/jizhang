# AI 智能记账与数据分析

## Goal

减少记账时需要手动填写和选择的字段，让用户可以用一句自然语言完成一笔账的草稿；在用户确认后安全入账，并基于真实账本数据提供可解释的消费总结、评价和整理建议。

AI 是辅助层，不应成为账务事实来源：金额、日期、账户余额、预算和统计口径仍由现有领域模型与服务计算，AI 只能提出结构化建议或基于已计算数据生成说明。

## Confirmed repository facts

- 项目是单用户 Vue 3 + Vite PWA、Fastify API、SQLite 存储的同源部署应用。
- 新建账单目前要求用户填写金额、类型、分类、账户、日期，并可填写备注和标签。
- 分类支持一层父模块与子分类；父模块不能直接用于记账，账单必须选择可入账分类。
- `packages/shared` 是预算、退款、周期和金额口径的唯一实现；前端不能自行重算财务数字。
- 服务端已经提供分类、账户、标签、账单、预算和统计数据；微信/支付宝导入已有预览、粗分类和人工确认流程。
- 项目目前没有 AI provider、模型配置、AI API 密钥管理或 AI 结果持久化设计。

## Requirements

### R1. AI 辅助记账

- 用户可输入类似“昨天午饭 35 元，微信支付”这样的自然语言。
- AI 返回待确认草稿，至少包含金额、收支类型、日期、备注、分类候选和账户候选；无法可靠识别的字段必须明确标为待补充。
- AI 不得直接写入账本；用户确认或修改后才调用现有账单保存路径。
- 用户仍可随时使用现有表单手动记账；AI 不可用、超时或网络断开时不能阻塞手动流程。

### R2. AI 分类建议

- 分类建议只能来自当前用户已有的可入账分类，不能凭空创建父模块或分类。
- 建议应返回置信度或可读的理由，允许用户一键改选分类；首个切片不要求从修正中自动学习。

## Future direction (separate follow-up tasks)

- AI 可基于服务端已计算的月度收入、支出、分类占比、预算使用和趋势，生成简短总结、亮点、风险和下一步建议。
- AI 输出必须能追溯到具体统计周期和数据指标；不能捏造金额、分类或趋势。
- AI 可提出重复分类、标签规范化、分类归并或异常消费的整理建议，但任何批量修改都必须逐项预览并由用户确认。

### R4. 隐私与可控性

- AI provider 采用可配置的服务端 HTTP 适配层，不在业务代码中写死 OpenAI、DeepSeek 或其他供应商。
- 至少支持配置请求地址、HTTP 方法、认证信息、请求头/请求体和响应字段映射，以便接入 OpenAI、DeepSeek 及用户自己的兼容接口。
- AI provider 和密钥只存在服务端配置，不能下发到浏览器或写入账单数据。
- AI 配置通过登录后的“设置”页面维护；页面可以显示当前是否已配置和脱敏后的摘要，但不能回显完整密钥。
- API key 在 SQLite 中只保存密文；服务端使用独立的 `JIZHANG_AI_ENCRYPTION_KEY` 解密，缺少该密钥时 AI 配置不可用并给出明确提示。
- 用户能够关闭 AI 功能；关闭或 provider 不可用时，基础记账、预算和统计保持可用。
- 发送给外部模型的数据范围、保存策略、错误处理和敏感字段脱敏方式必须在设计阶段明确。

## Acceptance Criteria

- [ ] 用户可以通过自然语言生成一笔待确认账单草稿，草稿字段与现有账单模型兼容。
- [ ] 用户确认前不会新增或修改任何账本记录；确认后复用现有校验和保存语义。
- [ ] 分类建议只展示当前可入账分类，并支持人工改选。
- [ ] AI 失败、超时、无配置或断网时，手动记账链路仍可用。
- [ ] AI 密钥不出现在前端构建产物、浏览器网络响应或账单导出中。
- [ ] 未登录用户不能读取、修改或测试 AI 配置。
- [ ] 数据库备份中不包含可直接使用的明文 API key；更换加密密钥时有明确的不可解密/重新配置行为。

## MVP scope

第一阶段确定为“记一笔”里的自然语言文本输入：AI 生成可编辑的账单草稿和分类候选，用户确认后复用现有保存路径。先验证最直接的减负价值；AI 月度评价和批量整理作为后续子任务，在第一阶段稳定后接入同一套服务端 provider、权限和审计边界。

## Confirmed product decisions

- 第一阶段使用文本输入，不把语音、图片 OCR 或聊天机器人纳入首个切片。
- AI 只生成待确认草稿和建议，不自动保存、不自动改分类，也不直接修改历史账单。
- 现有手动记账表单继续保留，AI 失败或关闭时不能影响基础记账。
- AI provider 配置通过设置页面完成，服务端只向前端返回非敏感配置摘要。
- AI provider 使用独立的设置页面；“我的”页面只保留入口，不内嵌长表单。
- 月度评价第一版只分析当前自然月，按用户点击生成，不保存评价结果，也不提供历史月份选择。
- 月度评价返回服务端聚合事实和 AI 说明两部分；每条说明必须引用返回事实中的 evidence id，前端不能用 AI 文本替代金额。
- API key 通过独立服务端加密密钥保护后持久化；不把完整密钥放进前端或账单数据。
- 常用 provider 使用 OpenAI-compatible / Responses 预设；高级自定义模式允许配置请求模板和响应字段映射，但只能使用受控的模板变量。

## Current follow-up slice

- `POST /api/v1/ai/monthly-evaluation` 已实现为登录保护的只读接口，按一次捕获的服务端时钟生成当前自然月 `[from, to)` 聚合。
- 外发给 provider 的内容仅包含收入、支出、分类占比、六个月趋势和明确标注周期的预算聚合值；不包含交易备注、标签、账户行或原始账单。
- 月度评价只在统计页点击后生成，服务端不保存评价；provider 返回未知 evidence id 或无依据的陈述时请求失败，不渲染未经验证的文案。

## Current follow-up: AI data organization

### Goal

让用户能发现标签/分类数据中的重复或不规范项，并在看到影响范围后逐项确认整理；AI 只负责解释、排序和提出建议，服务端负责事实、依赖检查和最终写入。

### Repository evidence

- 标签没有独立表，名称直接存放在 `transactions.tags_json`；现有标签重命名已经是服务端单事务全量改写，且会去重。
- 分类 id 还会被交易、预算快照、模板、周期账单规则和待确认 occurrence 引用；现有分类删除会软删除分类并停用相关未来规则，但保留历史账单。
- 现有平台账单导入已经提供“预览 → 选择/改分类 → 一次确认”的安全交互先例。
- 研究建议首版包含预览、版本/哈希前置条件、原子应用、审计和可条件撤销；异常先只做提示，不自动删账或改金额/日期/账户/备注。

### Recommended safe first slice

先做只读整理预览：检测精确/规范化重复标签、同类型且同父级的重复叶子分类，以及仅供参考的异常提示。预览返回 action id、影响数量、样例、阻塞原因和 confidence；不修改任何账本记录。

### Confirmed product decision

- 第一版必须包含分类合并，不再把它留到后续版本。

### Confirmed safe category-merge contract

- 只允许同一收支类型、同一父模块下的叶子分类合并；不允许把父模块直接并入叶子，也不允许跨收入/支出类型合并。
- 用户明确选择保留的目标分类；被合并分类不能是内建分类，目标可以是内建分类。
- 预览必须列出交易、模板、预算快照、周期账单规则和待处理 occurrence 的影响数量，以及任何阻塞依赖。
- 应用时在一个 SQLite 事务内迁移所有可迁移引用；已确认/已忽略的 occurrence 保留历史快照，不静默改写历史事实。
- 应用前校验预览版本/哈希；过期则整体拒绝。操作写入追加式审计记录，撤销仅在当前值仍等于操作后的值时允许。

### Implementation status

- 已完成服务端预览、AI 解释降级、分类/标签原子应用、审计迁移和条件撤销。
- 已完成 `/settings/ai/organization` 页面、逐项选择、确认应用和撤销交互。
- 已通过分类依赖、历史 occurrence、预览过期、撤销冲突、provider 数据脱敏和手机端浏览器测试。

## Next correction: semantic category analysis

### Confirmed user intent

- “数据整理”不应只寻找完全重复的分类名称。
- AI 需要分析现有分类下的账单语义，指出分类混杂、建议账单移动到更合适的现有分类，并可以提出新增分类建议。
- 当前实现只做重复名称检测，因此无重复项时快速返回“无需整理”是实现缺口，不是期望的产品行为。

### Blocking privacy decision

语义分类需要一定的备注/标签上下文；仅发送分类名称、数量和预算引用无法可靠判断“这笔账应该属于哪个分类”。已确认允许扫描时发送最近最多 200 笔有效账单的有限备注摘要（截断，并不发送金额、账户、日期），同时发送标签、当前分类和可选分类。页面必须明确显示该发送范围；账单级建议仍只做预览，不自动改账。

## Out of scope for the first slice

- 自动保存或自动改分类、自动删除或合并账单。
- 以 AI 取代现有预算引擎、余额计算、退款口径或统计聚合。
- 在没有用户确认的情况下创建分类、账户、标签或修改历史账单。
- 一次性实现语音、图片 OCR、发票识别、聊天机器人和所有平台的自动接入。
- 月度 AI 评价、趋势总结、异常分析、批量分类整理和标签自动学习。
- 将 AI 分类建议直接接入微信/支付宝导入流程；该流程保留现有关键字粗分和人工确认，后续单独规划。

## Planning status

需求已收敛，没有阻塞实现的产品问题；技术边界、错误降级、数据库兼容和测试替身记录在 `design.md` 与 `implement.md`。

## Proposed major follow-up: conversational AI assistant

### Goal

新增一个独立的 AI 助理页面，把现有记账应用能力变成可对话调用的工具：用户可以用自然语言记账、查询预算/统计、整理分类，也可以直接发送微信/支付宝账单文件，在同一段对话中完成解析、预览、修正和确认。

### Confirmed user intent

- AI 助理是应用的统一交互入口，不是散落在各页面的单独按钮。
- 文本消息可以调用现有记账、查询、评价和整理能力。
- 对话支持附件，至少包括现有微信 xlsx、支付宝 GBK CSV 导入格式。
- 用户希望尽量通过与 AI 交互完成现有功能，同时保留原页面作为可用的手动入口。

### Confirmed repository constraints

- 现有业务能力已经按服务/API 分层；AI 应调用这些受校验的服务，而不是生成 SQL 或在浏览器直接调用 provider。
- 平台账单导入已有 dry-run 预览、逐项选择、分类覆盖和确认写入，可直接作为对话附件工具的业务内核。
- 写请求受会话与 CSRF 保护；金额、预算、退款和周期口径必须继续由 shared/server 计算。
- 手机底部导航已验证为 6 项上限，不能直接添加第 7 个 tab；需要决定替换现有入口或从页面内进入。

### Initial interaction model

- 助理将消息解析为受控工具调用，如“生成记账草稿”“预览账单导入”“查询本月统计”“扫描分类建议”。
- 读操作可直接返回对话卡片；写操作返回结构化确认卡，用户确认后才调用现有写服务。
- 文件、工具结果和确认状态属于对话上下文；provider 密钥仍只保存在服务端。

### Blocking product decision

需要确认 AI 的写入权限模型：推荐“读取/分析可直接执行，任何新增、修改、删除、导入和批量整理都必须先显示结构化预览卡，再由用户点一次确认”。如果只允许 AI 填表不执行，交互会更保守但仍需跳回原页面；如果允许无需确认自动执行，则误识别会直接影响账本和预算，不符合现有安全边界。
