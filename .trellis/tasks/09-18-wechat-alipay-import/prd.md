# PRD：微信 / 支付宝账单导入

## 背景

数据页目前只能导入**本应用导出**的账单/转账 CSV。用户日常消费主要发生在微信、支付宝，
需要把平台账单导出后导入本应用，避免手工逐笔录入。

## 用户决策（已确认）

| 决策点 | 选择 |
|--------|------|
| 推进方式 | Trellis 任务：先规划再实现 |
| 分类映射 | **关键字粗分**到应用分类；分不准的落到「其他」，导入后可改 |
| 账户策略 | **自动创建**「微信」「支付宝」等账户（若不存在） |
| 真实样例 | 用户**会提供**真实导出文件，用于对齐列名与边界 |

## 目标

在「数据 → 导入」中支持：

1. 识别并导入**微信支付账单** CSV
2. 识别并导入**支付宝账单** CSV
3. 与现有「本应用账单 / 转账」导入并存；可重复导入（按稳定键去重）

## 非目标

- 不做图片/PDF 账单 OCR
- 不做平台 API 自动拉取（仅文件导入）
- 不完美还原平台侧分类树（只做关键字粗分）
- 不导入红包明细、余额变动、提现、信用卡还款等**非消费/非收入**流水（见过滤规则）
- 不修改已有本应用 CSV 的导入语义

## 功能需求

### R1 来源识别

- 自动识别文件属于：`wechat` | `alipay` | `jizhang-transactions` | `unknown`
- 识别失败时给出可读错误，**不得**半截写入
- 用户在 UI 选择导入类型时可强制指定；选「自动」时靠识别

### R2 编码与表头

- 兼容 **UTF-8 / GBK/GB18030**（微信/支付宝导出常见）
- 跳过账单文件顶部的说明/摘要行，定位真实表头
- 表头列名做别名匹配（如「金额」「金额(元)」「金额（元）」）

### R3 字段映射

| 平台字段 | 应用字段 |
|----------|----------|
| 交易时间 | `date`（本地日，忽略时分或仅用于排序） |
| 商品/商品说明/交易对方/备注 | `note`（优先商品；其次对方+商品拼接） |
| 收/支 或 交易类型方向 | `type`：支出 / 收入 |
| 金额 | `amountCents`（正整数分；去 `¥`/`￥`/千分位） |
| 交易单号/交易订单号/商户单号 | 去重 `id`（优先级见 R5） |
| 支付方式（可选） | 不直接写入账户名；账户由来源决定（R4） |

### R4 账户

- 微信账单 → 账户名「微信」
- 支付宝账单 → 账户名「支付宝」
- 若不存在则在**同一导入事务内**创建（type 可用「现金/电子钱包」语义，默认账户类型枚举中已有的电子类或 custom）
- 不因单行支付方式（如「零钱」「余额宝」「花呗」）拆成多账户（v1 简化：全部记入微信/支付宝主账户）
  - 说明：花呗/信用卡还款场景 v1 不建信用账户流水，仅避免误导入还款行（见 R6）

### R5 去重与幂等

- 稳定键优先级：
  1. 平台交易单号（微信 `交易单号`，支付宝 `交易订单号`）
  2. 若无单号：`sha1(source|time|amount|type|note)` 截断
- 应用内 `transactions.id` 使用 `wx-<单号>` / `ali-<单号>` / `hash-<digest>`，避免与 UUID 冲突
- 重复导入：`inserted` 增加，已存在行 `skipped`
- **整单事务**：任一行硬错误 → 全部回滚（与现有 import 一致）

### R6 行过滤（默认跳过且计入 `skippedIgnored` 或单独统计）

| 类型 | 规则 |
|------|------|
| 非成功 | 状态含「失败」「关闭」「异常」等 → 跳过 |
| 退款成功 | 微信「已全额退款」/「退款成功」等：可配置；**v1 默认：支出行若状态为退款成功则跳过**（避免与收入型退款重复）；若「收/支」已是「收入」且状态成功则**导入为收入+退款标记（无关联）或普通收入** → **v1：记普通收入，不自动勾 isRefund** |
| 转账/提现/充值/还款/红包 | 商品或交易类型含这些关键词且金额方向为支出时跳过（可开关，v1 默认跳过提现/充值/还款/红包；**普通转账到他人若带商品名则仍可能进「其他」**） |
| 余额/资金明细 | 无交易单号且类型为余额类 → 跳过 |
| 金额 ≤ 0 | 跳过 |

统计：`ImportResult` 扩展 `ignored`（被过滤行数）与可选 `warnings[]`。

### R7 分类关键字粗分

对 `note + 平台原始分类` 做大小写不敏感匹配，命中即映射；否则「其他」。

建议初始表（可放 `shared` 常量，后续可配）：

| 关键词（示例） | 分类 |
|----------------|------|
| 餐,饭,咖啡,奶茶,外卖,美团,饿了么,肯德基,麦当劳,小吃,烧烤,火锅 | 餐饮 |
| 地铁,公交,打车,滴滴,高铁,火车,机票,加油,停车,过路 | 交通 |
| 房租,水费,电费,燃气,物业,宽带 | 住房 |
| 淘宝,天猫,京东,拼多多,购物,衣服,鞋,数码,超市,便利店 | 购物 |
| 电影,游戏,会员,娱乐,KTV,旅游,门票 | 娱乐 |
| 其余 | 其他 |

收入侧：

| 关键词 | 分类 |
|--------|------|
| 工资,薪资,奖金 | 工资 |
| 退款 | 退款（`builtin-income-refund`） |
| 其余收入 | 其他收入 |

### R8 API

```
POST /api/v1/import/platform-bills
Content-Type: text/csv   (或 application/json 包一层 { source, csv }，见设计)

Body: CSV 原文
Query/JSON: source?: auto | wechat | alipay
```

响应：

```json
{
  "source": "wechat",
  "inserted": 12,
  "skipped": 3,
  "ignored": 5,
  "total": 20,
  "accountsCreated": ["微信"],
  "warnings": ["第 12 行金额无法解析，已跳过"]
}
```

（若坚持「整单失败」，则 warnings 仅用于非致命提示；致命错误仍 400。）

**与现有 import 的差异**：平台账单允许「可解析则跳过该行 + 计入 ignored」还是严格失败？
**PRD 定案**：平台账单采用 **宽松行级跳过 + 事务内只插入成功解析且未忽略的行**；
致命错误（编码无法识别、找不到表头、整文件无有效行且有脏数据）→ 400 整单失败。

### R9 前端（数据页）

- 导入类型增加：`自动识别` / `微信账单` / `支付宝账单` / 保持原「账单」「转账」
- `accept` 放宽：`.csv,.txt`（部分导出后缀为 `.csv` 或无后缀）
- 选文件后展示：
  - 识别结果（微信/支付宝/应用账单）
  - 笔数、日期范围、支出合计、收入合计
  - 将使用的账户、将自动创建的账户
- 确认导入 → 显示 inserted / skipped / ignored
- 文案说明：如何从微信/支付宝导出（简短步骤 + 指向 USAGE）

## 验收标准

| AC | 描述 |
|----|------|
| AC1 | 微信 UTF-8 样例导入成功，支出进「微信」账户，餐饮类正确粗分 |
| AC2 | 支付宝 GBK 样例导入成功，账户「支付宝」 |
| AC3 | 同一文件导入两次：第二次 inserted=0，数据无重复 |
| AC4 | 状态为失败/提现/红包的行不入账，且计入 ignored 或等价统计 |
| AC5 | 自动创建账户：空库导入后存在「微信」或「支付宝」 |
| AC6 | 本应用 CSV 导入行为不回归（既有 portability 测试全绿） |
| AC7 | 缺表头/非 CSV 文件 → 400，库内无部分写入 |
| AC8 | 单测覆盖：识别、编码、去重、过滤、关键字分类 |
| AC9 | 数据页 UI 可选微信/支付宝并完成导入闭环 |

## 依赖与约束

- 复用 `parseCsvWithHeader` / TransactionService 写入路径或直接 INSERT（与现有 import 一致风格）
- 不引入重型 CSV/编码依赖；GBK 可用 `iconv-lite` 或 Node 能力评估后定（见 design）
- 单用户应用，无多租户
- 1G VPS：解析在内存完成，限制文件大小（建议 ≤ 5MB，与 bodyLimit 一致）
